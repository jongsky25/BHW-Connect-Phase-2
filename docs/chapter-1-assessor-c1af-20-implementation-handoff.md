# C1AF-20 implementation handoff — Chapter 1 legacy authorization

## Scope and decision

This PR starts from C1AF-19 on `main` (`6db00d43`). It creates one private Chapter 1 write policy, then uses it both for revised component request/assessment scope and for the existing table guard beneath legacy RPCs. For the activated `bhw-reference-manual` Chapter 1 course, each write rechecks that the actor is an active assessor in the cohort, outside admin preview, has a current active Chapter 1 award under an enabled contract, and has no suspended or revoked chapter award or historical qualification. Global and cohort write flags and cutover must all be open. A named BHW must be active, in the same cohort, and in the assessor's catchment. Qualification rows are read under share locks, so a concurrent status change cannot pass unnoticed during that write.

The guard covers session creation, density/cancellation/completion, enrollment and attendance, delivery and activity records, planned lesson activity/scheduling writes, direct and activity-linked observations, and their direct table equivalents. It checks the session owner and recorder, and **every enrolled BHW** on each session write, including historical or imported roster rows. This prevents a session-org-only check from hiding an out-of-cohort learner. It preserves unrelated courses, including Gabay role-play, under their existing rules.

For an activated Chapter 1 course, the legacy binary assessment claim/decision and direct certificate route reject at the `assessments`/`certificates` guard. Direct `course_progress` certification, failed-assessment status, reset of either status, or reassignment to a different course/learner also rejects. The sole exception remains the C1AF-19 complete formal review's private `issuing` transaction, linked to its assessment and certificate. No generic admin override is introduced. Existing status-only historical assessor qualification lifecycle changes retain their separate audited administrator route; that exception cannot insert a new qualification.

## Verification

The focused PGlite test applies the exact C1AF-16 through C1AF-20 migrations to an isolated fixture. It covers certified session and observation writes, session ownership, an out-of-area BHW at enrollment, all-roster validation on later delivery, award revocation, inactive BHW, revoked historical qualification, preview persona, binary assessment/certificate writes, direct progress writes, and a Gabay/unrelated-course path. It revokes an award during an open formal attempt and confirms the next save is rejected. A second learner then completes both formal components and receives one certificate through the C1AF-19 review under the new guard. The migration does not change the old RPC signatures; the database triggers protect those RPCs and direct table writes alike. PR CI must additionally replay every migration on disposable full Supabase and run browser smoke. Do not run E2E against the pilot.

## Release and activation boundary

This migration seeds no cohort, approved contract, award, flag or cutover and does not activate Chapter 1. At approved merge, follow `docs/deploy-runbook.md`: check pilot health and Disk IO, apply this one migration once, verify the shared function, guards and triggers, then squash merge and let Vercel deploy. Confirm the pilot component registry, requests, assignments, formal attempts, reviews and reassessments remain empty; global and cohort writes and cutover remain off; the preexisting assessment and certificate counts remain unchanged. Smoke the manual, assessor working area, BHW request/result empty state and protected routes.

Live activation still requires reviewed component mappings, source revisions, rubric anchors, BHW test-release comparability and a further-practice record rule. Exercise each legacy RPC directly against a controlled, approved Chapter 1 cohort before opening writes, including certified, uncertified, out-of-area, preview, suspended and revoked actors and mixed rosters; retain non-Chapter-1/Gabay regression cases. C1AF-20b then verifies simulation parity. Do not infer authorization from a visible button, a course-org match, or a historical certificate alone.
